# 專案亮點

這份文件記錄 PartyMatch 主要工程決策。每個重點以「問題 → 做法 → 後續延伸」描述，方便從 README 的快速介紹延伸到具體實作。

## 1. 交易一致性與併發防護

**問題**：申請加入、團主審核、退款、撥款都會同時改動使用者餘額、群組名額、申請狀態與交易紀錄；如果只用「先查詢、再寫入」的流程，雙擊或併發請求可能造成重複扣款、重複退款或名額超收。

**做法**：核心交易流程以 Prisma transaction 包住，並把關鍵條件放進資料庫寫入條件中，例如餘額足夠才扣款、申請仍為待審核才可核准、群組仍有名額才遞增人數。寫入結果為 0 筆時直接視為狀態已被其他請求搶先改變。

**後續延伸**：為什麼前端 loading state 不能取代後端原子操作；如何設計 idempotency key；正式金流串接後哪些流程需要付款狀態對帳。

## 2. 群組生命週期狀態機

**問題**：共享訂閱不是單純貼文媒合，群組會經過招募、額滿、鎖定、填寫帳號資訊、啟用、確認、續訂或結束。每個階段可執行的操作不同，若散落在前端判斷，容易出現非法操作或狀態不一致。

**做法**：以 `Group.status` 作為核心狀態，後端負責驗證狀態轉換與金流副作用，前端只依 API 回傳狀態決定顯示哪些操作。完整流程見 [群組狀態機](../flows/group-state-machine.md)。

**後續延伸**：狀態機如何避免 UI 與後端規則分歧；續訂、申訴、成員退出這些例外流程如何回到主線。

## 3. 多情境退款與代管規則

**問題**：取消申請、審核未通過、成員退出、被團主移除、群組解散、申訴裁定都會影響 PM 幣歸屬，但每個情境的商業規則不同。

**做法**：退款、撥款與代管金額異動依情境拆開處理，避免把所有分支塞進同一個巨大函式。交易紀錄保留每次異動的來源，讓管理後台與測試案例都能追溯金額變化。

**後續延伸**：如何驗證金額不會對不上；正式金流接入後，平台內部代幣與外部付款狀態如何對應。

## 4. 資料權限與敏感內容遮罩

**問題**：團主、已加入成員、申請中使用者與訪客能看到的群組資料不同；共享帳密、成員服務帳號與附件讀取權限都不能只靠前端隱藏。

**做法**：後端在回傳群組與成員資料前統一套用遮罩邏輯，敏感欄位依角色與群組狀態決定是否可見。附件維持私有化讀取，需要時才由後端產生可用的讀取連結。

**後續延伸**：IDOR 風險如何檢查；為什麼資料遮罩要集中在後端；如何避免新增 API 時漏掉權限處理。

## 5. 通知同步與使用者操作保護

**問題**：通知輪詢會在背景更新資料，但使用者可能正開著群組詳情或審核頁面操作；如果背景資料直接覆蓋畫面，會造成 Modal 閃爍、表單消失或狀態跳動。

**做法**：通知依類型分成「需要刷新畫面資料」與「只需即時提示」兩類，並以通知類型與群組做合併去重。使用者正在查看相關群組時，背景更新會延後套用，避免打斷當下操作。

**後續延伸**：為什麼現階段使用 polling 而非 WebSocket；如何處理分頁離線、回到前景與過期資料同步。

## 6. 前端元件拆分與全域互動

**問題**：建立群組、群組詳情、管理群組等畫面一開始承載太多狀態、RWD 分支與業務邏輯，維護時很難判斷一個修改會影響哪裡。

**做法**：將大型元件拆成容器、步驟元件、展示元件、純函式工具與 Zustand store；訊息、通知、儲值等可由任何頁面觸發的全域 Modal，則用事件廣播集中處理，不讓 props 穿越多層中間元件。

**後續延伸**：什麼邏輯放 component、hook、store 或 API layer；為什麼沒有把所有狀態都塞進單一全域 store。

## 7. 測試與 CI

**問題**：這個專案的主要風險不在單一元件是否能 render，而是完整流程跨越多張資料表、多個角色與多個狀態後是否仍然一致。

**做法**：前端測試涵蓋共用元件、Zustand store 與核心頁面互動；後端測試涵蓋群組生命週期、申訴、續訂、通知、帳號流程與併發衝突情境。CI 在 push/PR 時自動跑 lint、測試與 build。

**後續延伸**：哪些情境適合單元測試、整合測試或手動測試；目前還缺少哪些 E2E 與監控。

## 8. 技術取捨

- **Polling 而非 WebSocket**：合購媒合聊天室不是低延遲交易系統，目前用 polling 可以沿用既有 HTTP 認證與部署模型，降低連線管理複雜度；若使用量成長或需要低延遲互動，再導入 WebSocket。詳見 [ADR-0002](../adr/0002-polling-over-websocket.md)。
- **Prisma db push 而非 migration 歷史**：專案仍在頻繁調整 schema 的開發階段，先用 `db push` 降低重構成本；正式上線或多人協作時，再切回 migration 流程保留完整變更紀錄。
