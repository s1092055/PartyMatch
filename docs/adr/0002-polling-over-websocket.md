# ADR-0002：訊息與通知用 Polling 而不是 WebSocket

**狀態**：已採用
**日期**：2025-12（訊息與通知功能初次實作時）

## 背景

群組聊天室、私訊、系統通知都需要讓使用者看到「別人剛剛做的更新」，不是純粹靜態頁面。常見做法是 WebSocket 或其他即時推播機制。

## 決策

目前用 polling（每 5 秒）取代即時監聽，登出時呼叫 `teardown()` 停止 polling。

## 理由

- MVP 開發階段，PartyMatch 目前使用情境是小規模合購群組（多則十幾人），沒有大量使用者同時線上、也沒有低延遲即時通訊的硬性需求，5 秒的更新間隔對聊天/通知這種用途體感差異不大
- Polling 用一般 REST 端點就能實作，不需要另外維護 WebSocket 連線的伺服器狀態（連線管理、心跳、斷線重連），架構更簡單，跟其餘所有功能一致走「Store 呼叫 REST API」這一套模式，不需要為了這一項功能另外引入一套通訊機制
- 後端部署在 Render 免費方案，長連線在免費方案下的穩定性跟資源限制都不如短連線的 REST 請求可預期

## 取捨

- 每個開著訊息中心的使用者每 5 秒打一次 API，使用者數量增加時請求量會線性成長，比 WebSocket 的推播模式更耗資源
- 即時性有上限（最多 5 秒延遲），不適合真正需要低延遲的場景（例如打字中提示）

## 未來

當同時上線人數變多、polling 請求量對伺服器造成明顯負擔，或需要更即時的體驗（例如打字中狀態、更即時的線上狀態）時，會評估改用 WebSocket 或 Server-Sent Events。見 [未來規劃](../portfolio/future-roadmap.md)。
