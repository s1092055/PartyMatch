# AI 協作說明

給履歷/作品集連結、或面試官問「這個專案用了多少 AI」時用。目的是誠實揭露協作方式，同時講清楚貢獻在哪裡。如果自己另外有沒被記錄進來的經驗（某個 bug 是自己肉眼抓出來、某個架構決策是自己堅持要求改的），優先用那些真實細節補充，第一手經驗比整理過的說明更有說服力。

## 協作方式

PartyMatch 的產品定位、核心功能規劃、使用者角色設計（一般使用者／團主／管理員）與整體使用情境由我主導。實作層面大量透過 AI 協作（Claude Code）產出程式碼，包含前端元件、後端 API、Prisma schema、Tailwind 樣式。

我的工作集中在：

- **產品與功能範圍**：哪些功能要做、優先順序、MVP 邊界在哪（見 [產品總覽](../product/product-overview.md) 的「不支援的功能」）
- **架構與設計取捨**：像 `shared/ui` 什麼時候該重新分類、design token 該不該拆成多個檔案，這類決策先聽 AI 說明 trade-off，再自己決定要不要做、做到什麼程度
- **程式碼審查**：跑過 code review 找出併發安全性、重複程式碼等問題並驗證修正（核准申請缺少狀態鎖導致可雙擊重複扣款、`DELETE /groups` 名額判斷 off-by-one 等 7 筆，見 [Bug 紀錄](../testing/bug-log.md)）
- **手動測試**：依 [手動測試計畫](../testing/manual-test-plan.md) 實際跑過主要流程

## 為什麼這樣做

對一個學習階段的作品集專案來說，重點不是完全不用 AI 手刻每一行，而是能不能讀懂並解釋 AI 產出的程式碼在做什麼、能不能在它有問題時看出來並要求修正、能不能做「這個功能該不該做」「架構該拆到什麼程度」這類 AI 無法替你決定的判斷。

整理這個專案本身也是在練這些能力：接手既有 codebase、追蹤功能的完整資料流（前端 → API → 後端 → 資料庫）、驗證流程正確性、把複雜的產品邏輯整理成可維護、可對外說明的文件。

## 面試時可能被問到的追問

- 「你自己寫過多少 code？」——誠實回答比例，不用刻意誇大或隱藏
- 「舉一個你自己抓到、AI 沒發現的問題」——準備 1-2 個具體案例
- 「AI 給你一個看起來能動、但架構不好的方案，你怎麼判斷？」——用專案裡實際的取捨案例回答
