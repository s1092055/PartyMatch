# AI 協作說明

這份說明是給履歷/作品集連結、或面試官主動問「這個專案用了多少 AI」時使用的。目的是誠實揭露協作方式，同時清楚呈現貢獻在哪裡。如果你自己另外還有沒被記錄進來的經驗（例如某個 bug 是你自己肉眼抓出來、某個架構決策是你堅持要求 AI 改的），優先用那些真實細節補充，第一手經驗永遠比整理過的說明更有說服力。

## 協作方式

PartyMatch 的產品定位、核心功能規劃、使用者角色設計（一般使用者／團主／管理員）與整體使用情境由我主導。實作層面大量透過 AI 協作（Claude Code）產出程式碼——包含前端元件、後端 API、Prisma schema 設計、Tailwind 樣式等。

在協作過程中，我的工作包含：

- **產品與功能範圍決策**：哪些功能要做、優先順序、MVP 邊界在哪裡（見 [產品總覽](../product/product-overview.md) 的「不支援的功能」）
- **架構與設計取捨的判斷**：例如 `shared/ui` 什麼時候該重新分類、design token 該不該拆成多個檔案——這類決策我會要求 AI 先說明 trade-off，再由我決定要不要做、做到什麼程度，而不是全盤接受 AI 的第一個建議
- **程式碼審查與問題排查**：跑過 code review 流程找出併發安全性、重複程式碼等問題，並實際驗證修正（例如核准申請缺少狀態鎖導致可雙擊重複扣款、`DELETE /groups` 名額判斷 off-by-one、維運腳本殘留呼叫已移除的資料表等 7 筆，見 [Bug 紀錄](../testing/bug-log.md)）
- **手動測試**：依 [手動測試計畫](../testing/manual-test-plan.md) 實際跑過主要流程，確認功能符合預期

## 為什麼這樣做

我認為對於一個學習階段/作品集專案，重點不是「完全不用 AI 從頭手刻每一行」，而是：

1. 能不能清楚讀懂並解釋 AI 產出的程式碼在做什麼、為什麼這樣設計
2. 能不能在 AI 產出有問題（安全性漏洞、邊界條件沒處理、過度複雜的寫法）時看出來並要求修正
3. 能不能做出「這個功能該不該做」「這個架構該拆到什麼程度」這類 AI 無法替你決定的判斷

這個專案的整理過程本身也是在練習這些能力：接手一個既有 codebase、追蹤功能的完整資料流（前端 → API → 後端 → 資料庫）、驗證流程正確性、把複雜的產品邏輯整理成可維護、可對外說明的文件。

## 面試時可能被問到的追問

- 「你自己寫過多少 code？」——誠實回答比例即可，不用刻意誇大或隱藏
- 「舉一個你自己抓到、AI 沒發現的問題」——建議準備 1-2 個具體案例
- 「如果 AI 給你一個看起來能動、但架構不好的方案，你會怎麼判斷？」——可以用專案裡實際的取捨案例回答（例如是否過早拆分 design system、是否過度使用某個 pattern）
