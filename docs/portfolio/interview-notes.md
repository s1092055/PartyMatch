# 面試講稿筆記

每段控制在 1-2 分鐘可以講完的量，面試官通常會打斷追問，不需要一次講完所有細節。以下是可以直接練習的講稿草稿，依實際面試時的追問彈性調整用詞即可。

## 1. 為什麼做 PartyMatch？

共享訂閱的合購媒合，現實中大多發生在 Facebook 社團、PTT 或 Discord 群組裡，靠留言、私訊跟人工記帳撮合。這個模式有幾個明顯問題：找到合適的人很耗時、也難以判斷對方信不信得過；付款紀錄散落在聊天記錄裡，一旦有糾紛沒有任何憑據；沒有審核機制，詐騙風險高；團主要手動確認每一筆轉帳，成員也搞不清楚自己的付款跟續訂狀態到底處理到哪。

PartyMatch 想解決的，是把「媒合 → 申請 → 審核 → 付款代管與確認 → 啟用服務」這整條路徑收斂到同一個平台上完成，讓團主跟成員都有清楚的角色介面，而不是繼續依賴私訊跟表單。這也是為什麼系統會設計出完整的群組狀態機、PM幣代管機制，而不是做一個單純的「貼文媒合板」。

## 2. 我的角色是什麼？

這個專案的實作大量透過 AI 協作（Claude Code）完成，我的角色集中在**決策**跟**把關**，不是逐行手刻每一個元件。具體來說：

- **產品與功能範圍**：哪些功能要做、優先順序怎麼排——例如目前刻意把「內部功能完善」（互評系統、信用分數動態調整、帳號恢復流程）排在「正式金流串接」之前，因為先把使用者看得到、摸得到的流程打磨完整，比先接一個還沒有完整規則的金流更有價值。
- **架構取捨的最終決定**：AI 提案通常不只一種做法，會附上 trade-off，但要不要做、做到什麼程度是我決定的。例如整理 `shared/ui/` 資料夾時，AI 一開始建議依複雜度切成 3 層資料夾，我要求先看實際檔案清單、用途分類的具體樣式，確認邊界清楚後才拍板用 2 層（`primitives/` + `group/`）而不是過度拆分；反過來 `docs/` 文件架構我也會要求拆得更細、寫得更完整，因為那次的判斷是「這是作品集整理，寧可完整也不要因為怕檔案多而縮手」。
- **程式碼審查與問題排查**：我會要求跑過完整的 code review 流程，實際抓出並要求修正過的問題包括：核准申請流程原本缺少狀態鎖，雙擊或併發請求可能造成同一筆申請被重複扣款；`DELETE /groups/:id` 的名額判斷寫錯門檻，已有成員加入的群組仍可能被直接刪除繞過退款邏輯；一個清空資料庫的維運腳本裡殘留呼叫已經移除的資料表，會導致腳本執行到一半噴錯、留下不一致的資料。
- **手動測試**：依照測試計畫實際跑過主要流程，確認功能符合預期後才算完成。

## 3. 技術架構怎麼設計的？

可以挑 [專案亮點](./project-highlights.md) 裡 2-3 個深入講，建議優先順序：
1. **交易安全性**（Prisma transaction + 條件式 updateMany）——這個最能展現對併發問題的理解，而且是我自己實測時真的抓到過漏洞的地方（見下一題）
2. **群組狀態機**——展現把複雜業務邏輯收斂成清楚資料模型的能力
3. **事件驅動的全域 Modal 架構**——如果面試官對前端架構決策比較有興趣，這個適合講「為什麼不用 props 傳遞」的取捨過程

每個亮點記得準備「為什麼這樣做」+「還有什麼替代方案、為什麼沒選」，面試官很常追問後者。

## 4. 我遇到什麼問題？怎麼解決的？

最具體的一個例子：在跑 code review 時發現「團主核准申請」這個 API 沒有防止同一筆申請被處理兩次——如果團主手滑雙擊核准按鈕，或網路延遲下使用者重試，兩個請求會幾乎同時抵達後端，各自通過名額檢查，導致同一位申請人被重複扣款、群組人數被灌兩次。原因是雖然名額檢查已經有做併發防護（條件式 `updateMany`），但「這筆申請目前是不是還是 pending 狀態」這件事本身沒有被原子化地檢查跟鎖定。解法是把申請狀態的轉換也改成跟名額檢查一樣的條件式 `updateMany` 模式——只有在 `status: 'pending'` 時才允許轉成 `approved`，寫入失敗就代表已經被別的請求處理過，直接回錯誤。這讓我更確定一件事：只要牽涉到「檢查後再寫入」的流程，只要有併發可能性，就要優先想「這個檢查跟寫入能不能合成一個原子操作」，而不是加 loading 狀態鎖前端按鈕就當作解決了（前端鎖只能防手滑，防不了真正的併發請求）。

其他技術決策點也可以視情況延伸：
- 多裝置登入 session 從單一 refresh token 改成 per-session key 存 Redis，同時要處理舊格式 token 的向下相容
- `shared/ui` 什麼時候決定要重新分類、依據什麼標準判斷一個元件算「泛用」還是「業務綁定」

## 5. 我怎麼測試這個專案？

依照 [手動測試計畫](../testing/manual-test-plan.md) 的優先級分類實測：先跑 P0 核心交易流程（申請 → 審核 → 付款代管 → 啟用），確認狀態機轉換跟金額異動都正確，再測 P1 次要功能跟 P2 邊界情況與 RWD。測試帳號用 seed 腳本建立的固定資料（不同信用分數、不同 PM幣餘額的帳號），方便重現「餘額不足」「信用分數不達門檻」這類邊界情境，而不用每次手動調資料庫。抓到的問題記錄在 [Bug 紀錄](../testing/bug-log.md)。

## 6. AI 在這個專案裡扮演什麼角色？我怎麼跟 AI 協作？

詳細版本見 [AI 協作說明](./ai-collaboration-note.md)。重點是誠實且有自己的判斷——不會講成「AI 幫我做了全部」，也不刻意隱藏 AI 的參與。這個協作模式對我來說更接近「資深工程師帶一個很快但需要盯緊的junior」：AI 產出速度快、涵蓋面廣，但架構要不要這樣拆、這個 trade-off 值不值得、這段邏輯有沒有漏掉併發情境，這些判斷要我自己把關，不能照單全收。

## 7. 未來會怎麼優化？

見 [未來規劃](./future-roadmap.md)，可以挑 1-2 個最有技術含量的深入講：
- **WebSocket 取代輪詢**：目前訊息 5 秒、通知 10 秒都是 polling，會講到為什麼現階段先選 polling（實作簡單、不需要額外的連線管理），以及之後要換成 WebSocket 時要處理哪些東西（斷線重連、多分頁狀態同步）
- **信用分數動態調整**：目前只是靜態欄位，之後要規劃加扣點的觸發規則跟歷史紀錄表，這題適合展現「怎麼在還沒有明確規則時，先把資料層設計得可擴充，而不是貿然生一個之後要砍掉重練的 schema」

- 準備 1-2 個「講到一半被問倒」也沒關係的坦誠說法，例如「這部分我目前是先用簡化版邏輯，還沒有處理 XXX edge case，如果要正式上線我會優先補這個」——誠實比硬拗更有說服力
- 上面的草稿是根據目前 codebase 事實跟這次對話中的真實決策過程寫的；如果你自己另外還有沒被記錄進來的經驗（例如某次卡了很久、某個決策其實猶豫很久才定案），優先用那些真實細節取代或補充這裡的內容，第一手經驗永遠比整理過的草稿更有說服力
