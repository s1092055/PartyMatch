# 面試講稿筆記

每段控制在 1-2 分鐘講完，面試官通常會打斷追問，不用一次講完所有細節。

## 1. 為什麼做 PartyMatch？

共享訂閱的合購媒合，現實中大多發生在 Facebook 社團、PTT、Discord 群組，靠留言、私訊跟人工記帳撮合。問題很明顯：找人耗時、也難判斷對方信不信得過；付款紀錄散落在聊天記錄裡，有糾紛沒憑據；沒有審核機制，詐騙風險高；團主要手動確認每一筆轉帳，成員也搞不清楚自己付款跟續訂到底處理到哪。

PartyMatch 把「媒合 → 申請 → 審核 → 付款代管與確認 → 啟用服務」整條路徑收斂到同一個平台，團主跟成員都有清楚的角色介面，不用再靠私訊跟表單。這也是為什麼系統需要完整的群組狀態機跟 PM幣代管機制，不是做一個單純的貼文媒合板就好。

## 2. 我的角色是什麼？

實作大量透過 AI 協作完成，我的角色集中在決策跟把關，不是逐行手刻每個元件：

- **產品與功能範圍**：哪些功能要做、優先順序怎麼排。例如「內部功能完善」（互評系統、信用分數動態調整、帳號恢復流程）排在「正式金流串接」前面，因為先把使用者看得到摸得到的流程打磨完整，比先接一個規則還沒定案的金流更有價值
- **架構取捨**：做法通常不只一種，要不要做、做到什麼程度是我拍板，而且會回頭修正發現不好用的決定。比如共用元件資料夾一開始拆成 `components/ui/`（shadcn 純元件）跟 `shared/ui/`（業務組合元件）兩個獨立資料夾，用資料夾位置強制區分有沒有業務邏輯；用了一陣子發現這個區分對開發沒有實質幫助，「兩個都叫 ui」反而在瀏覽專案時容易誤以為是重複、沒整理乾淨，後來合併成一個資料夾，改用命名慣例（kebab-case vs PascalCase）跟子資料夾做同樣的分類；`docs/` 文件架構則是我要求拆得更細、寫得更完整，因為這是作品集整理，寧可完整也不要因為怕檔案多而縮手
- **程式碼審查**：跑過完整 code review，實際抓出並修正過：接受申請流程原本沒防止同一筆申請被處理兩次，雙擊或併發請求會造成重複扣款；`DELETE /groups/:id` 名額判斷寫錯門檻，已有成員加入的群組還是能被直接刪除，繞過退款；一個清空資料庫的維運腳本殘留呼叫已經移除的資料表，執行到一半會噴錯留下不一致資料
- **手動測試**：照測試計畫實際跑過主要流程，確認功能符合預期才算完成

## 3. 技術架構怎麼設計的？

挑 [專案亮點](./project-highlights.md) 裡 2-3 個深入講：
1. **交易安全性**（Prisma transaction + 條件式 updateMany）——最能展現對併發問題的理解
2. **群組狀態機**——展現把複雜業務邏輯收斂成清楚資料模型的能力
3. **事件驅動的全域 Modal**——如果面試官對前端架構決策有興趣，適合講「為什麼不用 props 傳遞」的取捨

每個亮點準備好「為什麼這樣做」跟「還有什麼替代方案」，面試官很常追問後者。

## 4. 我遇到什麼問題？怎麼解決的？

一個具體例子：團主接受申請這個 API 原本沒防止同一筆申請被處理兩次——團主手滑雙擊接受按鈕，或網路延遲下重試，兩個請求幾乎同時抵達後端，各自通過名額檢查，導致同一位申請人被重複扣款、群組人數被灌兩次。名額檢查本身已經有併發防護（條件式 `updateMany`），但「這筆申請現在是不是還是 pending」這件事沒有被原子化地鎖住。解法是把申請狀態轉換也改成同樣的條件式 `updateMany`：只有 `status: 'pending'` 才准轉成 `approved`，寫入失敗就代表已經被別的請求處理過，直接回錯誤。

這件事讓我更確定：只要牽涉到「檢查後再寫入」，只要有併發可能，就要優先想這個檢查跟寫入能不能合成一個原子操作，不是前端按鈕加個 loading 鎖住就當作解決了——前端鎖只能防手滑，防不了真正的併發請求。

其他可以延伸的技術決策點：
- 多裝置登入 session 用 per-session key 存 Redis（而非單一 refresh token），登出或 refresh 只影響單一裝置
- `components/ui/` 底下怎麼判斷一個元件算「泛用」還是「業務綁定」

## 5. 我怎麼測試這個專案？

照 [手動測試計畫](../testing/manual-test-plan.md) 的優先級測：先跑 P0 核心交易流程（申請 → 審核 → 付款代管 → 啟用），確認狀態機轉換跟金額異動都對，再測 P1 次要功能跟 P2 邊界情況與 RWD。測試帳號用 seed 好的固定資料（不同信用分數、不同 PM幣餘額），方便重現「餘額不足」「信用分數不達門檻」這類邊界情境，不用每次手動改資料庫。抓到的問題記錄在 [Bug 紀錄](../testing/bug-log.md)。

## 6. AI 在這個專案裡扮演什麼角色？

詳細版本見 [AI 協作說明](./ai-collaboration-note.md)。重點是誠實、有自己的判斷——不會講成「AI 幫我做了全部」，也不刻意隱藏 AI 的參與。這個協作模式比較像帶一個很快但需要盯緊的 junior：產出速度快、涵蓋面廣，但架構要不要這樣拆、這個 trade-off 值不值得、邏輯有沒有漏掉併發情境，這些判斷要自己把關，不能照單全收。

## 7. 你怎麼確保 AI 產出的程式碼品質？

不是寫完一次就上，而是定期回頭跑完整的 code review。最近一輪不是等使用者回報 bug 才修，而是主動把整個專案拆成四個範圍（後端 routes、共用 stores/api/utils、建立群組/快速搜尋/探索頁、我的群組/訊息/帳號/認證頁面），逐一分角度審查——範圍切得夠小，AI 才會真的把每一行看過一遍，而不是掃過去給籠統結論。

這輪抓到 4 個真的會影響使用者的 bug，而且都不是型別錯誤這種一眼看穿的問題，是要追資料流才看得出來：系統公告 broadcast 用 `for...await` 逐一發送，中間一人失敗會讓後面所有人收不到；退出群組有兩個入口（`GroupDetailModal` 跟「我的群組」頁面）各自維護一份退出邏輯，其中一份漏了退出聊天室，資料不一致但沒有任何錯誤訊息；退出群組通知團主寫錯，用了「通知自己」的本地方法，團主端完全收不到通知也沒人發現；帳號設定儲存失敗被 `.catch()` 吞掉，因為失敗的回傳值是 `{ ok: false }` 不是丟例外，畫面還顯示成功的樂觀值。這幾個共通點是：都能正常執行、不會噴錯、只是在特定情境下悄悄壞掉——這正是 AI 產出程式碼最容易漏掉的地方，因為它不會主動去想「這個分支如果失敗會怎樣」。

另外抓到的問題裡，有些沒有直接動手改，而是先記錄成技術債（例如 billingCycle 沒鎖定計費週期、群組結束沒同步訂閱狀態），因為這些會改變行為、影響範圍更大，不是單純的邏輯漏洞修正，需要先想清楚才動。這個判斷——什麼該當場修、什麼該先記錄再排優先序——就是我在這個流程裡的角色。

## 8. 未來會怎麼優化？

見 [未來規劃](./future-roadmap.md)，挑 1-2 個最有技術含量的深入講：
- **WebSocket 取代輪詢**：目前訊息 5 秒、通知 10 秒都是 polling。回答時先講清楚這不是「還沒學會 WebSocket」，是評估過的取捨——polling 每次都是無狀態的 HTTP request，可以直接沿用現有的 token 驗證跟水平擴展模型；WebSocket 要多處理連線生命週期、斷線重連、身分驗證另外設計，未來後端多開一台實例還要加 pub/sub 才能讓不同連線的使用者互通訊息（可以順勢提到現有 Redis 可以拿來做這件事，展現有想過怎麼延伸）。延遲影響：這是合購媒合聊天室不是即時交易系統，5-10 秒延遲對體驗影響很小。最後給一個明確的「換的時機點」：使用者規模大到 polling 請求量變成後端負擔，或情境真的需要低延遲互動，才值得付出 WebSocket 的複雜度——面試官通常會欣賞這種「有明確門檻，不是為了炫技而換技術」的判斷
- **信用分數動態調整**：目前只是靜態欄位，之後要規劃加扣點規則跟歷史紀錄表——適合講「規則還沒定案時,怎麼先把資料層設計得可擴充，不要貿然生一個之後要砍掉重練的 schema」

## 練習提醒

準備 1-2 個「講到一半被問倒」也沒關係的坦誠說法，例如「這部分我目前是先用簡化版邏輯，還沒處理某個 edge case，正式上線會優先補這個」——誠實比硬拗更有說服力。如果自己另外有沒被記錄進來的經驗（卡很久的地方、猶豫很久才定案的決策），優先用那些真實細節取代這裡的內容。
