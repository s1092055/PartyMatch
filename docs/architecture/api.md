# API 總覽

後端提供一組 REST API，依資源分類（使用者、群組、申請、成員、訂閱、通知、對話、收藏、評價、服務目錄、PM 幣、檔案上傳、系統訊息、帳號留言、管理員後台），遵循標準資源導向命名慣例（GET/POST/PATCH/DELETE 對應查詢/建立/更新/刪除）。

## 認證層級

端點依需求分四種：**公開**（如服務目錄查詢）、**選擇性登入**（訪客可呼叫，登入後看到更多資料，如探索頁群組列表）、**需登入**、**需管理員**（如申訴裁定、系統公告發送）。認證 token 機制見 [認證機制](./authentication.md)。

## 設計原則

- 群組相關端點另外處理狀態機推進動作（啟用、確認、申訴、解散、續訂等），與一般 CRUD 分開
- 涉及金流的操作（申請、退款、撥款）在後端以交易方式保證原子性，前端不直接操作餘額
- 回傳「其他使用者」資料的端點會依對方的隱私設定遮罩敏感欄位

## 端點分類

依資源大致分為：帳號與登入、群組 CRUD、群組狀態機動作（鎖定、啟用、確認、申訴、續訂）、申請、成員、訂閱、通知、對話、收藏、評價、服務目錄、PM 幣、檔案上傳、管理員後台。狀態機動作與一般 CRUD 分開設計，避免把「推進流程」跟「編輯資料」混在同一支端點裡。

## 設計慣例

- **送出申請即代管扣款**：不是等團主接受才扣款，申請當下就會先從餘額扣除並轉入代管，取消/退回時再原路退款
- **金流一律後端重新計算**：涉及金額與名額的操作，後端一律依方案資料重新推導金額、依代管總額反推撥款金額，不採信前端傳來的數字
- **併發下的重複處理防護**：同一筆審核/撥款/退款動作可能因為使用者雙擊、或多分頁同時操作而被觸發兩次，這類端點在資料庫層級做了條件式的搶佔處理，確保只有第一次呼叫會真正生效，重複的呼叫會拿到明確的「已被處理」回應而不是重複執行副作用
- **裁定結果只影響金流方向，不影響成員資格**：申訴裁定只決定該筆代管款項退還給哪一方，不會連動把任何人移出群組
- **隱私遮罩在回傳前套用**：任何會回傳「其他使用者」或「其他成員」資料的端點，都會先依隱私設定/角色關係遮罩敏感欄位，才回傳給前端
